# Development log — 2026-09-01

## Product-profile assembly additions

1. A maintained MOS-family product may now append source-owned ZDS assembly
   units through `ASM_SOURCES_EXTRA` and the matching target-relative object
   paths through `ASM_OBJECT_RELATIVE_EXTRA`.
2. The generic port verifies that the two configured suffixes correspond
   exactly. With no additions, the existing upstream assembly source and link
   order remains byte-for-byte ordered as before; product additions are sorted
   only within their appended suffix.
3. The repository-root assembly, runtime-closure, and firmware targets
   propagate the profile inputs. The runtime audit permits a metadata-only
   undefined symbol only when the selected profile assembly object's target
   symbol table defines it; unsafe, missing, and duplicate profile source paths
   fail closed.
   No product name, symbol, source path, or behavioral assumption was added to
   generic build machinery.
4. The source-profile and runtime-tool tests cover the neutral surface, exact
   mapping guard, safe assembly-source selection, and empty-profile order
   preservation. `STARTHERE.md` records the maintained-source contract.
5. An adversarial follow-up moved the upstream assembly list into one shared
   build fragment and made both assembly and runtime closure consume that exact
   composition. Absolute, parent-traversing, non-canonical, duplicate,
   missing, wrong-suffix, outside-`src`/`src_startup`, and symlink-escaping
   declarations now fail before assembly. The runtime audit also rejects a
   missing or symlink-escaping linked object and derives provider authority from
   the target object's symbols, so an unlisted source or lexical XDEF cannot
   satisfy it.
6. Final validation passed the then-complete 108-test repository suite, the three
   focused source-profile tests, and the 16 focused runtime-tool tests. An EMOS
   caller then built both its ordinary and non-release fixed profiles through
   this machinery from the same explicitly selected prepared source tree.
   These are build/integration checks, not a source-to-release provenance
   claim; no emulator behavior or physical operation was performed.
7. A provenance follow-up found that the repository-root `worktree-check`
   ignored a caller-selected prepared tree and checked only the default stock
   pair. Root preparation and preflight now consume the explicit
   `MOS_MAINTAINED_SOURCE`/`MOS_WORKTREE` pair. A dry-run regression proves
   both selected paths reach the fail-closed preparation checker, preventing a
   product build from authenticating one source pair while compiling another.
8. The same adversarial review found that assembly output-directory symlinks
   were rejected only later by the runtime audit, after an assembler recipe
   could already have followed one. The profile preflight now rejects a
   symlinked object root, parent component, or output before assembly, and the
   runtime audit independently rejects a symlinked linked-object root. A
   behavioral runtime test also proves that provider permission comes from the
   selected target object's symbol table rather than the maintained source's
   lexical `XDEF`. The expanded repository suite now contains 109 tests; the
   focused runtime-tool suite contains 17 tests.

## Actual target-step provenance

1. The repository-root build now accepts an optional `PROVENANCE_DIR` for one
   freshly initialized build session. Initialization refuses stale contents
   and symlinked path components; recorded steps refuse pre-existing records,
   outputs, dependency files, maps, and linker traces. The ordinary empty
   setting preserves the pre-existing compiler, assembler, and linker recipes.
2. A generic recorder executes each target C compile, wrapped or direct target
   assembly, and final firmware link. It records normalized actual argv/cwd,
   its own digest, executable and declared nested-tool digests and version
   output, an exact deterministic child environment, response files, inputs
   discovered through compiler/assembler/linker dependency files, before/after
   input stability, and output digests. Record publication is atomic and
   no-clobber; unsafe path-component escapes, undeclared dependencies, changed
   inputs, command failure, and post-command validation failure produce no
   success record and remove safely addressable untrusted outputs.
3. Final-link evidence preserves the ordered object/archive list, validates
   direct object digests against their compile/assembly producer records, and
   hashes the resulting ELF, link dependency file, map, and captured nonempty
   `ld --trace` output. The assembly records also bind the prepared-worktree
   metadata, generated manifest and sources, translation/diagnostic tools, and
   direct assembler. Each C object record also captures a sanitized Clang
   `-###` probe and fails unless its one selected external assembler resolves
   to the exact GNU as executable hashed in that record. The actual driver
   command also carries `-fno-integrated-as` and a toolchain-local `-B` prefix;
   merely declaring a nested executable is not treated as proof of use.
   Version and driver-probe transcripts are normalized before hashing, so root
   relocation does not create a path-only digest difference.
4. A fresh stock `firmware-check` exercised the complete path and produced 36
   files: one session marker, 17 C records, 17 assembly records, and one final
   link record. The link record covered 33 ordered inputs, 32 direct producer
   records, 34 dependency inputs including the linker script, and a nonempty
   trace. The focused recorder suite covers stale state, input mutation,
   undeclared dependencies and response files, poisoned environment removal,
   direct assembly, producer mismatch, symlinked input/output parents,
   post-failure cleanup, and GNU ld's additional phony dependency rules.
5. Runtime-archive construction and ELF-to-BIN/HEX conversion remain outside
   actual-step recording. The linker record hashes the exact runtime archive;
   the existing firmware verifier still checks the derived binary. Product
   source/preparation/profile authority and release eligibility remain the
   owning product gate's responsibility; the recorder is intentionally not a
   sandbox or an attestation issuer.
6. Product profiles may now scope flags consumed by one selected C source using
   `C_SOURCE_CPPFLAGS_RELATIVE` and `C_SOURCE_CPPFLAGS_EXTRA`. This keeps
   role-specific definitions out of common-unit commands without embedding a
   product source name in generic machinery. Invalid or unselected scoped
   sources fail at Make parse time. Adversarial review found that the initial
   check accepted `%` as a Make filter and target pattern, which would have
   applied the supposedly local flags to every matching C target. The final
   interface rejects pattern-bearing selectors and its regression proves that
   `%` fails before any recipe is emitted.
7. Recursive runtime builds now receive the caller-selected toolchain, Python
   interpreter, and prepared source root explicitly. Direct entry through the
   port Makefile therefore records the same root authority as the repository
   firmware path instead of silently falling back to runtime defaults.
8. The ignored virtual environment has its own `PYTHON_ENV` evidence root.
   Python executable records therefore normalize below that root, allowing a
   product gate to authenticate the interpreter symlink without permitting
   symlinks inside the tracked `BUILD_TOOL` authority.
9. The initial rehearsal passed the then-current 128 repository tests, a clean
   stock `firmware-check` provenance build, and the ordinary no-provenance
   `firmware-check` path. The external-assembler selection flags did not change
   the linked image: its ELF SHA-256 remained
   `8c75f002813d9cff08b4190514c985760b6f6ea1bd75df9635066907a13867d7`.
   That raw rehearsal predates the session-marker corrections below and is not
   retained as evidence. After those corrections, all 131 repository tests
   pass; fresh product captures remain required.
10. Adversarial review then found that the initial fresh-directory marker was
    byte-constant, so its digest could not distinguish independent capture
    sessions. Each initialization now writes a random 128-bit hexadecimal
    session ID into the no-clobber marker; every step continues to prehash and
    postcheck that exact marker. A paired regression proves independent
    initializations cannot share either the ID or marker digest. Final-link
    recording also rejects a declared producer made by different recorder
    bytes, a different session marker, or a non-object-producing step kind.
11. The response-file review found that a declared top-level `@file` could
    contain an unrecorded nested response reference. Schema v1 now rejects any
    `@` byte in a declared response file before executing the target command;
    recursive, tool-specific response parsing remains deliberately
    unsupported. Current MOS/EMOS recipes use no response files.
