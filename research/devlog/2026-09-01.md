# Development log — 2026-09-01

## Product-profile assembly additions

1. A maintained MOS-family product may now append source-owned ZDS assembly
   units through `ASM_SOURCES_EXTRA` and the matching target-relative object
   paths through `ASM_OBJECT_RELATIVE_EXTRA`.
2. The generic port verifies that the two configured suffixes correspond
   exactly. With no additions, the existing upstream assembly source and link
   order remains byte-for-byte ordered as before; product additions are sorted
   only within their appended suffix.
3. The repository-root assembly, runtime-closure, and firmware targets
   propagate the profile inputs. The runtime audit permits a metadata-only
   undefined symbol only when the selected profile assembly object's target
   symbol table defines it; unsafe, missing, and duplicate profile source paths
   fail closed.
   No product name, symbol, source path, or behavioral assumption was added to
   generic build machinery.
4. The source-profile and runtime-tool tests cover the neutral surface, exact
   mapping guard, safe assembly-source selection, and empty-profile order
   preservation. `STARTHERE.md` records the maintained-source contract.
5. An adversarial follow-up moved the upstream assembly list into one shared
   build fragment and made both assembly and runtime closure consume that exact
   composition. Absolute, parent-traversing, non-canonical, duplicate,
   missing, wrong-suffix, outside-`src`/`src_startup`, and symlink-escaping
   declarations now fail before assembly. The runtime audit also rejects a
   missing or symlink-escaping linked object and derives provider authority from
   the target object's symbols, so an unlisted source or lexical XDEF cannot
   satisfy it.
6. Final validation passed the then-complete 108-test repository suite, the three
   focused source-profile tests, and the 16 focused runtime-tool tests. An EMOS
   caller then built both its ordinary and non-release fixed profiles through
   this machinery from the same explicitly selected prepared source tree.
   These are build/integration checks, not a source-to-release provenance
   claim; no emulator behavior or physical operation was performed.
7. A provenance follow-up found that the repository-root `worktree-check`
   ignored a caller-selected prepared tree and checked only the default stock
   pair. Root preparation and preflight now consume the explicit
   `MOS_MAINTAINED_SOURCE`/`MOS_WORKTREE` pair. A dry-run regression proves
   both selected paths reach the fail-closed preparation checker, preventing a
   product build from authenticating one source pair while compiling another.
8. The same adversarial review found that assembly output-directory symlinks
   were rejected only later by the runtime audit, after an assembler recipe
   could already have followed one. The profile preflight now rejects a
   symlinked object root, parent component, or output before assembly, and the
   runtime audit independently rejects a symlinked linked-object root. A
   behavioral runtime test also proves that provider permission comes from the
   selected target object's symbol table rather than the maintained source's
   lexical `XDEF`. The expanded repository suite now contains 109 tests; the
   focused runtime-tool suite contains 17 tests.
