# BUILD-003 — EMOS size comparison, 2026-10-15

The installed EMOS build reproduces exactly. The reported ZDS size also
reproduces, but the original 5,892-byte comparison mixed two accounting methods
and different identity strings. Most extra ZDS bytes are in MOS command code
and strings; ZDS's runtime is actually smaller than AgonDev's. Two isolated
experiments demonstrate a ZDS link within flash without deleting EMOS features,
but the experiment needs runtime qualification before becoming a firmware
solution. No hardware or installed firmware was touched.

The controlling task is [BUILD-003](../docs/tasks/BUILD-003.md). This report
completes the initial analysis tranche and supplies preliminary recommendations;
promotion and acceptance remain pending. Machine-readable results are in
[`evidence/build-003-summary.json`](../evidence/build-003-summary.json).

## 2. The original size figures were not comparable extents

| Measurement | AgonDev installed build | ZDS reported size build |
| --- | ---: | ---: |
| Summed module code, constants and ROM copies of initialized data | 128,473 | 134,514 |
| Additional reset-to-vector address span | 149 | 149 |
| Flat image extent from address zero | 128,622 | 134,663 |
| Flash capacity minus extent | 2,450 | −3,591 |

ZDS's `Used` excludes the 149-byte span from `0x6B` to `0x100`. AgonDev emits
that span in its flat binary, including a 79-byte Fab descriptor and 70 bytes
of fill. The descriptor occupies existing address space; it does not extend
the image. ZDS's HEX also omits 71 bytes of reset-segment `DS` storage already
counted in the module's size. Its HEX contains 134,443 explicitly addressed
bytes and 220 holes, with no overlapping records. Hole filling produces the
134,663-byte analysis extent. An overflowing or failed-link HEX is retained
   for analysis only.

Consequently, the original reported difference is 5,892 bytes, while the
same-accounting image-extent difference is **6,041 bytes**. The reproduced ZDS
image requires 3,591 bytes of extent reduction to fit, rather than the original
3,442-byte `Used` overflow.

The sums close exactly: no bytes are unassigned at the module/accounting

explanation. By emitted section kind, the 6,041-byte payload difference is

114-byte `mos_errors` pointer table in ROM constants while ZDS initializes it

`mos` alone adds 3,625 code bytes, 1,225 constant bytes and 114 initialized-data
bytes. All seventeen maintained assembly modules that occupy ROM have the
same module sizes across the two builds: 9,702 bytes in each. The additional
assembly root containing globals occupies RAM. Translation/label spelling
does not explain this size gap. Equal assembly sizes are not a new claim of
bytewise or behavioral equivalence.

The script also paired 394 generated C code labels with ELF function sizes.
Notable diagnostic spans include `mos_cmdMEM` (988 versus 286 bytes),
`mos_exec` (1,771 versus 1,256), `editline` (2,464 versus 1,966), and
`mos_DIRFallback` (1,202 versus 752). Conversely, ZDS has smaller spans for
several FatFS/path functions. These are navigation aids: compiler inlining and
intervening tables mean a named span need not represent identical standalone
work in both compilers. Module totals are the additive accounting authority.

## 4. Identity and compatibility-edit controls

The original ZDS assessment lacked all three EMOS identity defines. It compiled
`UNVERSIONED-DO-NOT-DEPLOY` for source identity, build identity and status.
An isolated control with the installed identity reduces ZDS size by 14 bytes,
to 134,500 used bytes and a 134,649-byte extent. Two unsuccessful command-line
string-quoting attempts were preserved; the successful control supplies explicit
defines in the experimental C copy, with that source difference recorded.

Building AgonDev with the two ZDS compatibility edits, while retaining the
installed identity, reduces its image by 48 bytes to 128,574. The reduction is
in `emos.c`; moving declarations does not change `mos.c`'s load size.

After both controls, the **matched-input extent difference is 6,075 bytes**:
`5,892 + 149 − 14 + 48`. The original discrepancy is explained, and these
small mismatches do not reverse its overall conclusion.

## 5. Measured compaction experiments

| Native size control | ZDS used bytes | Image extent | Free / over capacity | Link result |
| --- | ---: | ---: | ---: | --- |
| Reproduced original assessment | 134,514 | 134,663 | −3,591 | Rejected |
| Matched identity | 134,500 | 134,649 | −3,577 | Rejected |
| Shared printf calls, `fpdumy.obj` | 132,097 | 132,246 | −1,174 | Rejected for ROM overflow |
| Above plus identical generated-literal pooling | 129,895 | 130,044 | **+1,028** | Passed |

1. **Shared printf calls:** The inherited `-genprintf` option expands constant
   format strings into sequences of runtime helper calls inside callers.
   Recompiling with `-NOgenprintf` reduces source payload by 4,225 bytes but
   adds 1,821 runtime bytes. The resulting net reduction is 2,404 bytes before
   resolving floating-format helper dependencies. `mos.c` contributes 2,659
   bytes of source reduction. This is measured option-dependent code generation,
   not an inference from similar disassembly.
2. **Runtime resolution matters:** The first `-NOgenprintf` link also had
   undefined `__u_dtof` and `__u_dtog`; its smaller size alone was not a valid
   result. Linking vendor `fpdumy.obj` adds one `RET` byte and resolves those
   symbols, yielding a net **2,403-byte** saving. These are floating-operation
   stubs, not a working floating-point formatter. The installed AgonDev
   formatter already disables floats, and the scanned source contains 214
   `printf`/`sprintf` calls, 200 conversions and no floating conversion.
   That supports a non-floating policy; it does not qualify dummy-based runtime
   behavior or arbitrary future format strings.
3. **Literal duplication:** Exact NUL-delimited duplicate inventory finds
   2,259 redundant bytes within ZDS modules after matching identity, including
   1,703 in `mos.c`. Those raw counts are opportunities, not promised savings.
   A narrower experiment pools only byte-identical generated `L__` constants
   composed of `DB` records in `STRSECT`, redirects their references, and
   reassembles/relinks. After `-NOgenprintf` it saves **2,202 actual bytes**,
   including 1,647 in `mos.c` and 358 in `emos_uart_probe.c`. Every `CODE`
   segment size remains unchanged. Five focused analysis tests cover escaped
   strings/control bytes, redirection, section exclusion and invalid HEX.
4. **Combined result:** The two valid size experiments save **4,605 bytes**
   relative to matched-identity ZDS. The ordinary linker passes its original
   ROM bounds, overlap and unresolved-symbol checks. Nothing is silently
   omitted, placed beyond flash, or compressed behind an unaccounted loader.
   This is an offline size proof. No emulator, target runtime, physical test,
   installation, or production promotion was performed.

## 6. Recommendations for discussion

1. Prioritize the printf generation choice and repeated literals before
   considering feature removal. They have measured savings sufficient to make
   this pinned build fit under native ZDS, with only 1,028 bytes of headroom.
   That is insufficient evidence for fitting the separately proposed UART
   integration; its measured generic sender alone is larger than that margin.
2. Review and qualify a non-floating printf runtime path against all sixteen
   inventoried formatter spellings, including widths, precision, long values,
   return counts and raw newline behavior. The vendor dummy object is an
   experimental dependency resolution, not an approved product remedy.
   Keeping complete floating support would require a separate size measurement.
3. Prefer explicit shared constants in maintained EMOS source, or a narrowly
   specified and tested build pass if selected by the Author. The generated
   assembly pooling script establishes the opportunity; it is not yet a
   maintained-source solution. Shared literal addresses can differ, and any
   code relying on distinct literal addresses or writing literals must be
   audited. The C declaration-movement and `memcpy` edits also need owner review.
4. Keep the full module/function inventories as the next optimization map.
   The remaining compiler differences include register allocation, frame setup,
   inlining and helper selection; this tranche does not attribute each
   instruction to a particular compiler pass. ABI and functional regression
   evidence is still necessary. There is no basis here for blaming local-label
   naming, a larger ZDS runtime, or a single globally inferior compiler.
